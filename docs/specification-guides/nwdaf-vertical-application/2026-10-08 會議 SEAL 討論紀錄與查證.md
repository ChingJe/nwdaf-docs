## 3. SEAL 是什麼

### 3.1. 定位與 vertical application 的定義

SEAL 的全名是 Service Enabler Architecture Layer for Verticals。TS 23.434 的範圍寫明，它規定的是支援「vertical applications over the 3GPP system」的架構與程序。這一點與經理的說法相符。

「Vertical application 是 3GPP 網路以外的服務」則不是規格的定義。TS 23.434 §3.1 的定義只有一句：「An application catering to a specific vertical.」Vertical 指的是產業領域，定義沿用 TS 22.104。

經理舉的例子（智慧製造、智慧交通、無人機）和規格提到的例子相符。但「在網路之外」不是條件：TS 23.434 §5.1 說明 VAL 服務的提供者與 PLMN 營運者可以是同一個組織。

**未能確認：** TS 22.104 不在本地，vertical domain 的定義內容沒有看到。

### 3.2. 由來與年代

「SEAL 支援 4G」成立。TS 23.434 同時適用 EPS 與 5GS，位置管理與網路資源管理都定義了對 EPC 的介面，例如 SCEF 的 T8 與 PCRF 的 Rx。

「從 4G 的年代就開始討論」則沒有規格依據。TS 23.434 Annex F 的變更歷史顯示：

| 日期 | 事件 |
| --- | --- |
| 2019-01 | 規格骨架，V0.0.0 |
| 2019-06 | 核准後發行 V16.0.0，屬於 Release 16 |

5G 架構規格 TS 23.501 的第一版 V15.0.0 在 2017-12 發行，早於 SEAL 的起草。

規格沒有記載 SEAL 的由來。最接近的只有 Introduction 的一句話，說架構考量了 mission critical 與其他 vertical application 的共通能力；Annex B 另有與 mission critical 共用架構的對照表。

一篇論文（Shah 等，2020）的說法是：3GPP 在 Release 13 制定 MCPTT 時定義了群組、身分、配置、金鑰等輔助服務，之後各產業都需要類似的服務，所以抽成共用的一層。這是論文的說法，不是規格的內容，見[文獻筆記第 11 篇][lit-11]。

**解讀：** 「網路對應用開放能力」這件事在 4G 就有（SCEF），所以經理的直覺有道理；但 SEAL 這份規格本身是 5G 時代的產物。

### 3.3. 服務清單

TS 23.434 §6.1 列出十項 SEAL 服務：

| 定義在 TS 23.434 | 定義在其他規格 |
| --- | --- |
| 位置管理、群組管理、組態管理、身分管理、金鑰管理、網路資源管理、通知管理 | 資料遞送（SEALDD，TS 23.433）、網路切片能力使能（NSCE，TS 23.435）、ADAE（TS 23.436） |

另有四項由 TS 23.434 的其他章節指向：AIMLE（TS 23.482）、空間錨點、空間地圖、數位資產。

經理說的「身分驗證」對應兩項：身分管理負責驗證應用層的使用者並發放 token，金鑰管理負責提供金鑰。

依據：[TS 23.434 §1][s1]、[§3][s3]、[§5][s5]、[§6.1][s61]、[Annex B][sB]、[Annex F][sF]；[TS 23.501 Annex R][t501]。

## 4. 位置管理的例子

經理的例子是：UE 啟動後，UE 上的 SEAL client 把位置回報給 SEAL server 存起來；VAL server 要知道某些 UE 的位置時去問 SEAL server，它回覆最後一次收到的位置。

骨架是對的。規格的程序比這個例子多三件事：

**回報是受設定控制的，不是 UE 自發的。**
- LM server 把回報設定下發給 LM client，內容是「要什麼資訊」與「哪些事件觸發回報」（§9.3.3）。
- 觸發條件有很多種，例如移動距離、經過時間、換基地台。經理說的「UE 啟動後回報」最接近其中的 initial registration。
- LM server 也可以隨時要求立即回報。這時如果要求的是這台 UE 自己的位置，使用者會被詢問是否同意（§9.3.4）。

**LM server 的位置來源不只 LM client。**
- LM server 可以經 T8 向 SCEF、經 N33 向 NEF、經 Le 向 GMLC 取得位置，也可以向第三方的位置伺服器取得（§9.2.2、§9.2.4.3）。
- 多個來源的位置可以融合，得到較準確的結果。

**回覆的不一定是「最後一次回報的位置」。**
- VAL server 查詢時，LM server 先檢查儲存的位置是否仍有效，例如計時器是否到期。有效才直接回覆（§9.3.9 步驟 2）。
- 沒有有效的位置時，LM server 會重新取得：觸發立即回報，或向營運者取得。
- 訂閱式的回報中，LM server 還可以向 NWDAF 取得 UE 的預測位置來回覆（§9.3.8 步驟 3）。

VAL server 使用位置的方式有三種：一次性查詢、訂閱、觸發回報，各有對應的 API（§9.4）。

依據：[TS 23.434 §9.2][s92]、[§9.3][s93]、[§9.4][s94]。更完整的整理見 [SEAL 02][seal-02]。

## 5. SEAL 與核心網路的關係

### 5.1. SEAL 可以代替應用使用核心網路

這個說法成立。TS 23.434 §6.2 說明 SEAL server 可以用 3GPP 的介面與網路通訊，也可以使用 SCEF、NEF 對外的 API；動詞是 may。

明文使用 NWDAF 分析的 SEAL 服務有：位置管理、網路資源管理、組態管理、NSCE、ADAE、AIMLE。

「取得分析後結合本地資料再回給 VAL」也有具體的程序。ADAE 的切片應用效能分析（TS 23.436 §8.3）就是把 NWDAF 的切片分析、OAM 的效能資料與自己的應用 session 分析合在一起，產生應用層的結果。

要補充的是：**多數條文沒有寫路徑。** 寫出「經 NEF 的 AnalyticsExposure」的只有網路資源管理的 §14.3.3.4。其他服務多半只寫「使用 NWDAF 的某項分析」，沒有寫直接還是經 NEF。

### 5.2. 應用不必經過 SEAL

「VAL 或 UE 不會直接跟核心網路溝通」這句話，在伺服器這一側不正確。

- **規格明寫 VAL server 可以直接使用 NEF。** TS 23.434 §14.2.2.1 的原文是：「The Network resource management server and VAL server act as authorized API invoker to consume services from the Core Network northbound API entities like NEF」。
- **規格為 VAL server 定義了直接接到核心網路的參考點。** 例如 VAL server 與 UPF 之間的 N6（§14.2.5.16）。
- **三份規格的架構圖都把 VAL server 與 SEAL server 並列畫成 AF。** 見 TS 23.434 圖 A-1、TS 23.436 圖 5.2.2-3、TS 23.482 圖 5.2.1.1-2。這一點是看圖檔確認的，圖中的文字無法做字串比對。
- **VAL server 可以自己擔任 SEAL server 的角色。** TS 23.434 §14.2.4.3 說某些部署中，VAL server 可以承擔網路資源管理 server 的角色。
- **NWDAF 的規格也不要求經過 SEAL。** TS 23.288 允許 AF 經 NEF 訂閱分析，也允許 NWDAF 向 AF 收集資料。這兩條路都只要求對方是 AF。

規格沒有任何一句要求 VAL 必須使用 SEAL。第 4 章架構需求的主詞全部是「The SEAL shall」，規定的是 SEAL 要提供什麼；第 5 章對取得 SEAL 服務用的是 may。

**解讀：** 規格也沒有一句明文寫「SEAL 的服務是選用的」。從每項服務各有獨立的 client、server 與 API 來看，可以只用其中幾項。「服務全部是選用的」這個明確的說法出自 Shah 等（2020）的論文。

### 5.3. 隔離與安全不是 SEAL 的目的

經理說「跟核心網路溝通需要 authentication 之類的保護，可以透過 SEAL 把它隔開」。規格沒有這樣寫。

- 在 TS 23.434 全文搜尋 hide、abstract、isolate、shield、complexity 這類字，沒有任何一句說 SEAL 用來隔離 VAL 與核心網路。
- 規格寫出的 SEAL 目的是共用，以及有效率地使用與部署。
- **對外部應用做認證、授權、遮蔽敏感資訊，是 NEF 的功能**（TS 23.501 §6.2.5）。隱藏營運者網域的拓樸，是 CAPIF 的架構需求（TS 23.222 §4.3.2）。
- SEAL 的安全規格 TS 33.434 保護的是 SEAL 自己的介面與應用層的使用者。它沒有任何關於 SEAL server 對 NEF 的專門條文。

**解讀：** SEAL server 面對核心網路時，自己就是一個 AF，要接受 NEF 或 CAPIF 的認證與授權。VAL server 直接面對核心網路時也一樣。SEAL 讓應用少做一些事，但它不是安全上的閘道。

### 5.4. UE 這一側

UE 這一側與經理的說法相符，但原因不是 SEAL。

- 規格的模型中，VAL client 經 SEAL client 使用 SEAL 的服務；VAL client 與 VAL server 之間另有 VAL-UU，獨立於 SEAL。
- 圖 6.2-1 中，通往 3GPP 網路的線只畫在 SEAL server 這一側。
- NWDAF 的規格也一致：UE 上的應用不直接面對 NWDAF，而是經使用者平面連到 AF，由 AF 收集資料（TS 23.288 §6.2.8.1）。

**解讀：** 核心網路對外的 API 本來就是給伺服器側的 AF 用的。UE 與核心網路之間是接取的關係，不是 API 的關係。規格沒有一句寫「VAL client 不得直接與核心網路互動」，只是模型裡沒有這樣的參考點。

依據：[TS 23.434 §4][s4]、[§5][s5]、[§6.2][s62]、[§14.2][s142]、[Annex A][sA]；[TS 23.501 §6.2.5][t625]；[TS 23.222 §4][c4]；[TS 33.434 §5][sec5]。

## 7. NWDAF 的定位

### 7.1. AI for Network

這個說法抓到了重心，但說得偏窄。

- **資料來源不只 NF。** NWDAF 也向 OAM 與 AF 收集資料，其中包含 UE 上的應用經 AF 提供的資料。
- **分析的消費者不只 NF。** AF 可以經 NEF 取得分析。
- **NWDAF 本身不做控制。** TS 23.288 §5.1 說明怎麼使用分析由消費者決定。
- 「AI for Network」與「取代規則式的操作」不是規格的用語。

### 7.2. 應用層能不能參與 NWDAF 的訓練

報告者在會中說「好像辦不到」，並說 NWDAF 頂多是資料來源。這個判斷要修正：

| 機制 | 應用層能不能參與 | 依據 |
| --- | --- | --- |
| NWDAF 之間的水平式 FL | 不能。訓練服務的提供者與消費者都限於含 MTLF 的 NWDAF | TS 23.288 §7.10.1、§7.11.1 |
| NWDAF 與 AF 的垂直式 FL | 可以。AF 可以當 client，也可以當主導的 server | TS 23.288 §5.4、§6.2H |

垂直式 FL 中，AF 當 server 時，NWDAF 用網路資料算出中間結果交給 AF，AF 可以使用非標準的 Analytics ID，推論的結果可以留在 AF。這是標準裡唯一讓 NWDAF 替應用側的任務出力的訓練機制。

但這條路和 SEAL 沒有接上。TS 23.288 全文沒有出現 SEAL、AIMLE、ADAE；AIMLE 的規格也沒有說自己可以當這個 AF。

依據與細節見[第 01 篇][ml-01]第 3、4 節與[第 02 篇][ml-02]。

## 8. 無人機的碰撞偵測

報告者提到的應用是 TS 23.436 §8.14 的 Collision Detection Analytics。經理問它是不是架構在 SEAL 上，答案是肯定的：這項分析由 ADAE server 提供，而 ADAE 是 SEAL 服務。

| 項目 | 內容 |
| --- | --- |
| 誰提供 | ADAE server |
| 誰使用 | 例子有 VAL server、位置管理 server、UAE server、無人機應用的伺服器 |
| 資料來源 | 核心網路的 NF（例子是 GMLC、NWDAF）、ADAE client、位置管理 server 與 client、第三方位置伺服器，以及儲存歷史資料的 A-ADRF |
| 收集什麼 | UE 之間的測距與 sidelink 定位的資料或分析、UE 的位置 |
| 判定條件 | 請求中給一個距離，UE 之間小於這個距離就算偵測到碰撞 |
| 輸出 | 目標 UE、可能碰撞的 UE、可能碰撞的時間與位置；選填的有移動方向、速度、信心水準 |

三點補充：

- **這項分析不限於無人機。** 資料輸出的說明中，移動裝置的例子包含無人機、V2X 裝置、機器人、帶著 UE 的人。
- **條文沒有寫怎麼使用 NWDAF。** NWDAF 與 GMLC 只出現在資料來源的例子裡，沒有服務操作，也沒有 Analytics ID。唯一的線索是資料輸出中提到 Relative Proximity analytics。
- **演算法沒有規定。** 條文只說 ADAE server 執行分析相關的操作。

**未能確認：** 無人機的應用使能層（UAE，TS 23.255）是否建立在 SEAL 上。TS 23.255 不在本地。本地能確認的只有：UAE server 被列為這項分析的消費者，TS 23.434 把無人機的指揮控制通訊列為網路資源管理的使用例子。

依據：[TS 23.436 §8.14][d814]。

## 9. Daisy 以 AIMLE 的形態出現

經理的構想是：Daisy 原本的任務請求、尋找訓練端、發送任務，可以變成 AIMLE 的服務；發布任務的 App 變成 VAL server。經理也說還沒有看 AIMLE 定義了哪些服務。

**結論：輪廓相符。** AIMLE 的水平式 FL 程序和這個構想的流程一致，角色也對得上。但有幾個步驟和經理描述的不一樣，另有一件事規格沒有。

以下只查規格這一側，沒有檢視 Daisy 本身。

### 9.1. 角色怎麼對應

| 通用 FL 框架的角色 | AIMLE 的實體 | 依據 |
| --- | --- | --- |
| 發布任務的管理後台 | VAL server | TS 23.482 §8.3.1 |
| 協調者：選成員、排程、下發訓練設定 | AIMLE server | §6.11、§8.12 |
| 聚合者 | AIMLE server | §8.12.2.1 步驟 9 |
| 訓練端 | AIMLE client，在 UE 上 | §8.12.2.1 步驟 7 |
| 模型倉庫 | ML repository，也存成員的註冊資訊 | §5.2.3.4、§8.11 |

- AIMLE server 與 VAL server 可以放在同一個實體（Annex A.5）。
- UE 上除了 AIMLE client 還有 VAL client，也就是應用本身。兩者之間的參考點 AIML-C 沒有定義 API。

### 9.2. 流程怎麼對應

| 步驟 | AIMLE 的程序 | 誰對誰 | 與經理的描述相比 |
| --- | --- | --- | --- |
| client 加入並上報能力 | §8.7 註冊 | AIMLE client 對 AIMLE server | 相符。上報的是支援的操作與模型類型，不是能訓練哪幾個具體的模型 |
| 查詢有哪些 client | §8.8 discovery | VAL server 對 AIMLE server | **不同。** 見下方 |
| 挑選參與者 | §8.9 selection、§8.10 participation | VAL server 對 AIMLE server，AIMLE server 再對各 client | **不同。** 見下方 |
| 發布訓練任務 | §8.3 訓練請求 | VAL server 對 AIMLE server | 相符 |
| 訓練與聚合 | §8.12 HFL | AIMLE server 對各 client | 相符 |
| 模型派發 | 無 | | **規格沒有。** 見第 9.3 節 |

**查詢時拿不到能力。** 經理說 VAL server 可以問「每個 client 上報的能力是什麼」。規格中，能力是查詢的條件，不是回應的內容。VAL server 給條件，拿回符合條件的 client 識別碼清單（表 8.8.3.2-1）。規格沒有讓 VAL server 讀取單一 client 資料的 API。

**挑選不是 VAL server 一個人決定。** 分三層：

1. VAL server 提出名單或條件。
2. AIMLE server 執行選擇，逐一向候選的 client 確認是否願意參與。
3. client 可以拒絕。同意的才組成 client set。人數不足最低要求時，整個選擇失敗。

**訓練請求不帶模型本身。** VAL server 給的是模型識別碼加位址，或一組需求讓 AIMLE server 去倉庫挑。請求中必須指定用哪些資料集，規格假設各 client 上的資料集已經準備好。

**訓練是多輪的訂閱，不是一次推送。** AIMLE server 為每個 client 設定排程並建立訓練訂閱，client 訓練後回報，AIMLE server 聚合。下一輪重新走選擇、確認、訂閱。聚合的方法規格只給一個例子：取平均。

### 9.3. 模型派發

經理舉的例子是：後台要部署新模型時，把設備的 ID 交給 server，由 SEAL 層把模型送到這些設備，並回報哪些設備已經收到、已經更新。

**TS 23.482 沒有這個程序。** 規格中模型到達設備的方式是：

- 設備自己來取（§8.2）。
- 設備訂閱後，倉庫有新模型時被通知（§8.2）。
- 作為訓練設定的一部分，被告知模型的識別碼與位址（§8.12）。

最接近的是 §8.20 的服務操作控制：VAL server 可以指定一批 client，請求中可以帶取模型的位址。但它的語意是啟動或停止一個操作，回報的狀態只有 start 與 stop，沒有「已收到」或「已更新」。

另外兩點：

- **規格沒有用 SEALDD 傳模型的說法。** TS 23.482 提到 SEALDD 的地方，只用來設定流量的 QoS。SEALDD 的規格 TS 23.433 不在本地，所以只能說 TS 23.482 沒有這個用法，不能說 SEALDD 做不到。
- **規格的「模型更新」方向相反。** §8.21 是使用端回報模型效能下降而觸發的重新訓練，不是後台決定換模型。

### 9.4. Stage 3 的落地程度

AIMLE 不只有架構描述。Stage 3 的 TS 29.482 與 TS 24.560 為上面多數程序定義了 HTTP API，本地有對應的 OpenAPI 檔。註冊、查詢、選擇、參與確認、訓練請求、HFL 訓練都有。

實作前要知道三件事：

- **HFL 的訊息放不了模型權重。** Stage 2 說 client 回報的是模型參數。但 OpenAPI 中，client 回報的 `hflTrngOut` 型別是 `PerfParams`，裡面只有準確率、precision、recall、F1、均方誤差、平均絕對誤差六個數值。回給 VAL server 的 `trainOut` 也是同一個型別。這一點已直接在 `TS24560_Aimlec_HFLTraining.yaml` 與 `TS29482_AIMLES_MLModelTraining.yaml` 兩個檔案中確認。
  - **補充（2026-10-14）：** 上面說的是每輪訓練的回報訊息。Stage 3 另有兩個和模型有關的欄位：下行的訓練請求帶模型的識別碼與位址，client 也可以主動向 server 取得模型本體；啟動與停止訓練的服務操作（§8.20）有一個選填的聚合位址 `mlMdAggregUri`，說明是用來送 model updates，但沒有規定怎麼送。所以正確的說法是：Stage 2 要求 client 回傳模型參數，Stage 3 的回報訊息沒有欄位可放，只在另一個程序留了一個位址。細節見[第二條線的第 03 篇][ml-03]。
- **UE 上的 client 是 HTTP 的接收端。** 參與確認、HFL 訓練等都是 AIMLE server 對 client 發 HTTP 請求，所以 Stage 3 的註冊多了一個必填的 `aimleClientUri`。UE 在 NAT 後面時怎麼被連到，規格沒有處理。
- **不少 API 還不穩定。** AIMLE 的 34 個 OpenAPI 檔（TS 29.482 與 TS 24.560）中有 17 個的版本帶 alpha，包含 HFL 訓練的那一個。推論沒有 OpenAPI。

**未能確認：** 權重放不進訊息是刻意的設計（權重一律走別的管道），還是尚未完成，從規格看不出來。

### 9.5. 規格沒有告訴你的事

把一個既有的 FL 框架做成 AIMLE，下面這些要自己決定。規格不是明說不規定，就是全文找不到。

| 主題 | 規格有的 | 規格沒有的 |
| --- | --- | --- |
| 聚合 | 一個例子：取平均 | 演算法、加權方式、每輪最少回報數 |
| 模型格式 | 模型以識別碼表示；互通資訊由廠商自訂 | 檔案格式、序列化方式 |
| 模型傳輸 | 模型本身或一個位址 | 從位址取模型的協定、大型模型的處理 |
| 訓練程式 | 無 | client 端的訓練程式怎麼來、訓練迴圈、超參數 |
| 訓練資料 | 前提是資料集已備妥並有識別碼 | 識別碼由誰配發、資料怎麼收集與標註 |
| 輪數與失敗 | 提到訓練排程與剩餘輪數 | 輪數怎麼決定、等多久、部分 client 失敗怎麼辦 |
| 隱私保護 | 無 | secure aggregation、differential privacy 等字全文零筆 |
| UE 內部的介面 | AIML-C 的一句定義 | 應用怎麼把資料交給 AIMLE client、怎麼拿到模型 |

垂直式 FL 的訓練協調明寫不在這個 Release 的範圍（§8.18.2 的 NOTE）。水平式 FL 是 AIMLE 唯一有完整訓練步驟的 FL 程序。

依據：[TS 23.482 §8.2][a82]、[§8.3][a83]、[§8.7][a87]、[§8.8][a88]、[§8.9][a89]、[§8.10][a810]、[§8.12][a812]、[§8.20][a820]、[第 9 章][a9]、[Annex A][aA]；[TS 29.482][a29]；[TS 24.560][a24]；[OpenAPI][oapi]。

## 10. 對研究方向的意義

以下是**解讀**，不是規格的內容，也不是已決定的方向。

**經理的大方向有規格支持。** 一般性的 FL 屬於應用層，NWDAF 的強項是網路資料。SA6 自己的研究報告也這樣說：TR 23.700-82 §4.2.2 列出既有方案沒有涵蓋的情況，其中一條是「VAL UE 可以被選為 FL client，其他工作組沒有考慮」。

**報告者問的「走深還是走寬」，查證後的看法是走深，重點放在 AIMLE。** 理由是 Daisy 與 AIMLE 的 HFL 程序對得上，而且 AIMLE 有 Stage 3 的 API 可以對照實作。

**NWDAF 不必退到只當資料來源。** 兩邊之間有一條垂直式 FL 的路。規格在這條路上留了很多空白：標籤怎麼提供、樣本怎麼對齊、AIMLE server 能不能兼任參與的 AF。如果要保留 NWDAF 在研究中的位置，這是最直接的接點。

**把 Daisy 做成 AIMLE 時，會先遇到兩個實際的問題。** 一是模型權重在 Stage 3 的訊息裡沒有位置，二是經理舉例的模型派發沒有對應的程序。這兩件事要自己設計，設計的結果也可以是研究的貢獻。

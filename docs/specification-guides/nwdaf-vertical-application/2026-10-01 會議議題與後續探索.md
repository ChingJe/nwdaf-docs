## 1. VAL 與 SEAL 的支援關係及使用義務

核心問題是：一個應用原本就有 client 和 server，SEAL 究竟替它完成哪些工作？應用是否必須依賴 SEAL，才能開始提供服務？

### 1.1. SEAL 將共用支援工作提供為服務

**目前的答案是：VAL 描述產業應用的功能；SEAL 將多種應用反覆需要的支援工作，定義為可供使用的共用服務。** 這些工作可以是配置管理、身分管理、位置管理、群組管理、網路資源管理，也可以是 ADAE 的分析或 AIMLE 的 AI/ML 支援。

例如，應用伺服器需要為某次服務通訊取得網路資源時，可以向 SEAL 的網路資源管理服務提出需求，由該服務處理網路側的協調。應用仍負責自己的業務功能，以及何時需要提出這項需求。SEAL 的「enablement」可以具體理解成提供這類支援能力，使應用能依標準程序使用它們。

這裡的依賴應逐項看：選用網路資源管理時，該段資源請求就依賴相應服務；選用 AIMLE 訓練時，訓練任務就依賴相應程序。**僅由「VAL」這個角色名稱，不能推導所有應用都必須使用同一套 SEAL 服務。** 特定應用規格是否另有必選功能，仍須另外核對。

因此，VAL–SEAL 的分層可先理解為應用功能與支援服務的分工。圖上的上下位置本身不足以說明服務的必用性、全部通訊的經過路徑，或應用的完整啟動程序。SDK 則是支援功能的一種提供形式；把 SEAL client 放進 App，仍需說明它負責哪項服務。

### 1.2. 應用提出需求，SEAL 承接支援工作

以手機上的應用與後端為例：應用準備開始一次服務通訊，希望取得較高的資料傳輸速度或較低的延遲。這是為了說明分工的情境；先假設手機已能把服務請求送到後端。

若這個應用選用 SEAL 的網路資源管理服務，可以把關係理解成三步：

1. **應用後端提出需求：** 依自己要提供的服務，向支援服務說明這次通訊需要的網路資源條件。
2. **SEAL 的支援服務處理資源請求：** 評估需求，與網路協調所需資源。實際的網路資源仍由底層網路處理。
3. **應用後端取得結果：** 支援服務回覆資源請求結果；在成功流程中，應用的服務通訊建立，資源完成分配。

**應用負責提供什麼服務；SEAL 承接的是該服務所需的一項支援工作。** 這就是此例中「Service Enablement」的具體意思。SEAL 有提供服務的 client／server，是因為這些支援工作本身也需要請求、處理與回覆，與應用自己的業務責任分開。

這個例子回答的是老師問的「取得資源能否由 SEAL 協助」。它從應用已能提出請求開始，沒有回答手機如何找到後端或完成註冊；這些問題在下一節分開看。對應的資源請求程序見 §1.5。

### 1.3. 註冊、發現與通道建立需要分別看

老師列出的幾項工作，可能涉及不同的對象與程序：

| 想完成的工作 | 本次查到的支援 | 尚不能據此推導的部分 |
| --- | --- | --- |
| 使用服務前取得配置 | 配置管理 client 向配置管理 server 取得 VAL UE configuration data；程序預先要求能安全存取 server | 配置內容由相應 VAL service 規格決定，不能假設其中必定有所有應用 server 的位址 |
| 找到可使用的 SEAL API | SEAL 服務 API 在 CAPIF core function 發布與發現 | 這不等於通用的 VAL client 尋找自己應用 server 的程序 |
| 註冊與服務選擇 | 規格的 SIP 信令控制模型包含使用者註冊、服務選擇、路由及位址解析等功能 | 不能直接套用到所有採其他通訊方式的應用 |
| 取得服務通訊所需資源 | 網路資源管理服務接收 VAL server 的需求並協調網路資源，如 §1.2 的分工 | 取得資源不等於已完成全部應用登入、業務 session 或傳輸連線程序 |
| 支援 UE 與 UE 通訊 | §14.3.9 定義特定的 Uu-based UE-to-UE 通訊支援程序，可按應用需求協調 QoS flow | 這是特定通訊情境，不能直接替代 UE client 與 MEC server 的發現流程 |

因此，不能把「註冊」「發現」「通道建立」合成一項由 SEAL 統一完成的動作；也不能因為 VAL-UU 的細節超出 TS 23.434 範圍，就斷言所有工作都由廠商自行處理。可能涉及個別 VAL service 規格、所選 SEAL 服務、信令控制系統或底層網路規格。

### 1.4. VAL 的名稱與符合性要求

VAL 展開為 **Vertical Application Layer（產業應用層）**。它是功能架構中的定位，不是一套固定產品或執行環境。TS 23.434 §3.1 的相關定義可整理為：

| 名詞 | 定義的中文轉述 |
| --- | --- |
| Vertical application | 服務特定產業領域的應用 |
| VAL client | 提供對應產業應用客戶端功能的實體 |
| VAL server | 特定 VAL service 的伺服器應用功能之通用名稱 |
| VAL service | VAL service provider 向 VAL users 提供的服務之通用名稱 |
| VAL system | 支援一項 VAL service 所需的應用、服務與支援能力之集合 |

§3.1 沒有將「已使用 SEAL」列為 VAL client／server 的定義條件。因此，從角色定位來看，既有產業應用可對應為 VAL。這與「符合某項 3GPP 應用規格」是不同判斷；後者需要核對具體要求。若應用 server 與 SEAL server 進行 API 互動，§4.1.2-e 明確要求其 `shall conform to CAPIF`。

VAL 也可以包含應用專用的支援功能。例如，外部 TS 23.286 V18.7.0 §6.2 明確讓 VAE（V2X Application Enabler）client／server 在與 SEAL 互動時承擔 VAL client／server 角色。這個例子說明角色映射，並不選定 V2X 為研究方向。產業領域的術語定義另依 TS 22.104 §3.1。

**尚未完整回答的是：某個具體應用從啟動到開始服務，如何取得位址、完成認證／註冊，以及選用哪些 SEAL 服務。** 本次已說明 SEAL 能承接的具體工作，但還沒有選定一項 VAL service，將其專用規格與 SEAL 程序串成完整流程。後續應以這個缺口為主，避免再次只列出服務名稱。

## 2. OAM 資料與 NWDAF 分析各自帶來什麼資訊

核心問題是：ADAES 為什麼一方面向 NWDAF 要分析，另一方面還向 OAM 收資料？兩者的資訊有何差別？

### 2.1. 量測、網路分析與應用分析是不同的處理階段

**OAM 提供網路管理量測；NWDAF 可使用這些量測及其他來源產生網路分析；ADAES 再結合應用側資訊，回答特定應用的效能問題。** 所以 OAM 與 NWDAF 並不是互斥的資料來源，NWDAF 本身也能向 OAM 收資料。

OAM 是 Operations, Administration and Maintenance（操作、管理與維護）的統稱。此處 PM（Performance Management，效能管理）資料描述量測到的網路運作情形。例如，NWDAF 切片負載輸入表列有平均註冊 UE 數、平均已建立 PDU session 數及 NF 資源使用情形。這些值能描述切片狀態，卻還沒有直接回答「我的應用使用這個切片時，端到端延遲會是多少」。

NWDAF 的切片負載、service experience 統計或預測，是網路側已產生的分析結果。ADAES 的目標則可以是指定應用在特定區域、時間及切片條件下的效能。三者在資訊處理與問題範圍上有所不同。

### 2.2. 用切片應用效能的程序看資料如何組合

TS 23.436 §8.3 描述的需求是：消費者訂閱某個切片／切片實例的應用效能分析，指定區域、時間及其他條件。ADAES 接受訂閱後，可取得以下資訊：

| 來源 | ADAES 取得的內容 | 在這個問題中的意義 |
| --- | --- | --- |
| OAM，或經 NSCE 間接取得 | 目標切片／切片實例的 PM 資料 | 提供管理量測 |
| NWDAF | 切片負載或 service experience 的統計／預測 | 提供網路側分析 |
| VAL session 分析 | 在目標切片與區域使用服務的 session 效能 | 提供與特定應用服務相關的資訊 |

NSCE 是 Network Slice Capability Enablement（網路切片能力支援）。資料取得後，ADAES 對上述資訊進行抽象化或關聯，回報指定應用／server 使用該切片時的效能。例如，規格列出最小、平均、最大預測 RTT（往返時間）或端到端延遲。

因此，直接取得 PM 與取得 NWDAF 結果，可以提供不同處理階段的資訊；結合應用 session 後，分析範圍也更接近消費者所問的應用。這是依程序作的用途解讀，規格未固定融合演算法，也未要求每次都使用同一組來源。

### 2.3. 尚未查清楚的量測細節

前述三個 PM 項目來自 NWDAF 的切片負載輸入表，不能直接當成 ADAES §8.3 的必填 schema。要完整回答老師「OAM 到底送了什麼」，仍需選一組實際量測，確認量測名稱、產生者、取樣方式、管理物件及取得介面。

後續需補查 TS 28.552、TS 28.554、TS 28.532／28.550 與 NSCE 的 TS 23.435。目前已釐清不同資訊的定位，但尚未完成這個案例的全部資料來源追蹤。

## 3. AIMLE 的 FL 與 NWDAF 的 MTLF 是否使用同一套訓練流程

核心問題是：AIMLE 也有 client 訓練與 server 聚合，這是否就是我們先前做的 NWDAF／MTLF 訓練？取得 NWDAF 分析，是否表示訓練交給了 MTLF？

### 3.1. 輔助選擇參與者與執行訓練是兩項工作

**在目前對照的 HFL 程序中，兩套體系的參與者與服務契約不同。AIMLE 使用 NWDAF 分析協助選擇 clients，並不代表 NWDAF 接手了應用的本地訓練與聚合。**

HFL（Horizontal Federated Learning，水平聯邦學習）中，各端執行本地訓練，協調端聚合模型更新。這個計算形態可以相似，但要判斷是否使用同一套標準程序，還需要看請求者、訓練端、交換內容及結果交付對象。

例如，AIMLE server 可取得 UE mobility analytics，作為 client selection 的參考。被選出的 AIMLE clients 隨後仍按 AIMLE 的訓練排程使用本地 dataset，將模型參數回傳 AIMLE server 聚合。NWDAF 在這段提供的是選擇決策所需的資訊。

### 3.2. 兩套 HFL 的實際分工

| 工作 | AIMLE HFL | NWDAF HFL |
| --- | --- | --- |
| 提出需求 | VAL server 請求 AIMLE server 訓練 | AnLF／MTLF 所在的 NWDAF 向 FL server NWDAF 請求模型 |
| 協調與聚合 | AIMLE server | 含 MTLF 的 FL server NWDAF |
| 執行本地訓練 | AIMLE clients 使用已準備的本地資料 | 含 MTLF 的 FL client NWDAFs 使用本地或依資料收集程序取得的資料 |
| 交換訓練資訊 | AIMLE 的 HFL subscription／notification | 對應的 Nnwdaf 模型與訓練服務 |
| 交付結果 | AIMLE server 向 VAL server 通知訓練結果，可依配置存入 ML repository | FL server NWDAF 向請求模型的 NWDAF 提供模型資訊 |

在 AIMLE HFL 中，訓練請求之後還要選擇成員、確認參與能力、排程、下發模型、接收本地參數及聚合，必要時進入下一輪。這些工作由 AIMLE 程序承擔，沒有因為取得 mobility analytics 而轉移到 NWDAF。

相應 NWDAF FL 服務也不是一般應用可直接呼叫的通用訓練 API。TS 23.288 §7.10.1、§7.11.1 明列相應服務提供者與消費者 `limited to NWDAF containing MTLF only for Federated Learning`。

### 3.3. 對既有 MTLF 工作的意義

目前可以說明兩套 HFL 的分工，但還不能據此宣稱現有 MTLF 實作能直接接收 AIMLE 的訓練需求。若要共用實作，需另外核對任務、資料集、模型、排程及結果通知如何對接；會議沒有決定這種整合方式。

這個結論只針對本節的 HFL。AF–NWDAF VFL，以及 AIMLE split operation 提到 NWDAF 處理節點，是其他程序，分別在後續主題討論。

## 4. VFL 訓練完成後各端保留什麼，以及如何推論

核心問題是：先離開 3GPP 的角色名稱，一般 VFL 如何完成訓練？結果是集中成一個模型，還是各端保留一部分？推論時還要不要合作？

### 4.1. 各方用同一批樣本的不同特徵共同學習

**VFL（Vertical Federated Learning，垂直聯邦學習）的關鍵是對齊相同樣本、結合不同端持有的特徵。** 訓練完成後，模型資訊可以分散保留；是否需要各端合作推論，取決於所選模型與演算法。

因此，先說清楚某個 VFL 演算法的資料與計算，再把它對應到 AF、NWDAF 等角色，才容易判斷標準程序承接了哪些工作。切分神經網路層數不是所有 VFL 的共同定義。

### 4.2. 用垂直線性迴歸看訓練與推論

以下依 Yang 等人（2019）論文 §2.3.2、§2.4.2 與表 1–2 摘要，作為一般 VFL 解說：

| 參與者 | 持有的內容 | 計算責任 |
| --- | --- | --- |
| A | 特徵 `xA`、本地模型參數 `θA` | 計算局部值並更新參數 |
| B | 特徵 `xB`、本地模型參數 `θB`、標籤 `y` | 參與 loss 與梯度計算，更新參數 |
| C | 加密計算的協助功能 | 協助處理加密且加上遮罩的梯度 |

1. A、B 對齊共同樣本。
2. 各算局部值，加密交換 loss 與梯度所需資訊。
3. 梯度加密並加上遮罩後交給 C；解密回傳、去除遮罩後，各端更新參數。
4. 迭代至終止條件，A 保留 `θA`，B 保留 `θB`。
5. 推論時，各算局部預測，再由結果請求端相加：`θA·xA + θB·xB`。

這個案例訓練後仍需兩方合作推論；C 是加密協助者，不能直接等同 NEF。[論文原文][vfl-paper]

### 4.3. 再對照 NWDAF／AF 的程序

TS 23.288 的 VFL 程序也有樣本與特徵準備、交換中間訓練資訊、更新並保存本地模型，以及後續推論。這些步驟可以作功能對照，但不能只因步驟相似，就宣稱前述加密演算法已被完整規範。

特別是中間資訊的內容未在此 Release 完整標準化，仍需決定演算法與資料格式。規格亦允許 server 按模型能力等條件選擇部分或不選 clients 參與推論；這不保證任何 VFL 模型都能由 server 單獨推論。

**後續需要選定實際演算法，逐輪列出各端輸入、計算與傳送內容，再核對 3GPP 的角色及程序。** 一般 VFL 的原理已有例子；具體研究方案的完整映射尚未完成。

### 4.4. 原討論與規格依據

**討論時間：48:26–51:39。**

**原討論摘要：** 老師建議先撇開 3GPP，用普通 Wi-Fi 網路或 cluster 說清楚 VFL 如何運作：模型如何分配，server／client 傳遞什麼，訓練完成後各端保留什麼，以及推論如何進行。理解一般框架後，再將它映射到 NWDAF 的角色與程序。會中也討論不同 VFL 形式是否都能映射，但沒有確認哪些形式已被規格支持。

依據：Yang 等人（2019），*Federated Machine Learning: Concept and Applications* [§2.3.2、§2.4.2、表 1–2][vfl-paper]；TS 23.288 V20.2.0 [§6.2H.1][nwdaf-vfl-general]、[§6.2H.2.3][nwdaf-vfl-train]、[§6.2H.2.4][nwdaf-vfl-infer]、[§6.2H.3][nwdaf-vfl-content]。

## 5. 應用側標成 AIMLE 時，AIMLE client 在哪裡

核心問題是：若架構只畫應用側 AF／VFL server 與 NWDAFs 做 VFL，為何還要把應用側稱為 AIMLE server？原本的 AIMLE clients 是否仍參與？

### 5.1. 名稱要對應實際工作

**AF／VFL server 已能描述 TS 23.288 這段應用側 VFL 的角色。若再標成 AIMLE server，就需要指出它實際提供哪項 AIMLE 服務，以及由誰持有資料與執行計算。**

這不是所有 VFL 都必須有 UE 上的 AIMLE clients。TS 23.482 本身就描述不同的參與方式，需要先決定採用哪個程序，才能判斷 client 是缺漏，還是原本就不是該情境的參與者。

### 5.2. AIMLE 規格中的兩種 VFL 支援

| 情境 | 本地資料與計算在哪裡 | AIMLE server 承接什麼 |
| --- | --- | --- |
| UE 上的 AIMLE clients 參與 VFL（§8.18.2） | 各 UE clients 有不同資料域的特徵與本地資料，執行訓練 | 選擇成員、支援樣本綁定、評估能力，協調中間結果與更新資訊 |
| VAL servers 承擔 VFL server／clients（§8.18.2b） | 參與的 VAL servers 承擔 VFL 角色 | 選擇成員與特徵、對齊共同樣本、分配每個樣本的 correlation ID，啟動參與者 |

第一種情境缺少 AIMLE clients，就缺少原本應由它們承擔的本地資料與訓練工作。規格描述了協調角色，但也註明如何具體協調 VFL 訓練超出此 Release 範圍。

第二種情境中，AIMLE server 的工作是準備參與者與樣本：在授權條件下，透過 NEF 的識別解析支援對齊樣本，將相關資訊交給 VFL server／clients。之後的訓練與推論由它們進行，超出這個準備程序的範圍。此情境未要求 UE 上的 AIMLE clients。

### 5.3. 回到會議中的構想

如果只採 TS 23.288 的 AF 作為 VFL server、NWDAFs 作為 VFL clients 的程序，這段互動本身不要求再增加 AIMLE client。老師指出的缺口在於：圖中雖然加了 AIMLE 的名稱，卻尚未說明使用哪種 AIMLE 能力。

例如，想讓 AIMLE 提供樣本對齊支援，就必須核對輸入由誰提供、結果如何交給 AF／NWDAF，以及其對接程序。§8.18.2b 寫的是 VAL servers，不能直接換成 NWDAFs 就宣稱已存在完整標準橋接。

另一個會中臨時提出的想法是「應用端先 HFL，再與 NWDAF VFL」。這仍需說明兩階段是否處理同一任務、樣本與特徵如何銜接，以及前段模型如何供後段使用；目前尚未形成方案。

### 5.4. 原討論與規格依據

**討論時間：52:19–55:39。**

**原討論摘要：** 報告者提出讓 AIMLE 承擔 AF，與 NWDAF 做 VFL。老師看圖後指出，VFL 參與端現在以 NWDAF 的形式存在，原本的 AIMLE client 似乎不見了。報告者臨時提出讓應用側 clients 先訓練、聚合，再接入 VFL 的想法，但未形成清楚方案。老師認為，就當時畫出的互動，使用 AF／VFL server 已能描述應用側角色，AIMLE 的參與尚未被說明。

依據：TS 23.482 V20.3.0 [§8.18.2、§8.18.2b、§8.18.3][aimle-vfl]；TS 23.288 V20.2.0 [§6.2H.2.1.1][nwdaf-vfl-discovery]。

## 6. 應用側能做 AI，為什麼還需要 NWDAF

核心問題是：AIMLE／ADAE 看起來更能配合應用需求，能否直接完成 NWDAF 的工作？不同提供者的服務又如何互通？

### 6.1. 計算能力相似，服務資格與資料取得仍有差別

**能執行模型訓練或預測，不會自動取得相同的網路資料存取能力，也不代表提供了相同的標準服務。** 判斷分工需要看誰向誰提出需求、可取得哪些資料，以及承擔哪種服務角色。

NWDAF 是 5GC 的 NF，AnLF 產生分析、MTLF 訓練模型，透過對應的 Nnwdaf 服務提供能力。ADAES 提供應用分析，能協調應用與網路等來源；需要網路服務時可承擔 AF 角色，也可使用 AIMLE 支援。AIMLE 則提供應用側模型與任務相關操作。

例如，第 2 題中 ADAES 取得 NWDAF 的切片負載分析，再結合應用 session 資訊。這段是服務合作。若改由 ADAES 自行算出「網路切片負載」，仍需證明它能取得所需資料、支持相同分析定義及提供相應介面，不能僅憑它具有 AI 能力就認定可取代 NWDAF。

### 6.2. 應用側已有可互通的 API，但仍要核對支援範圍

標準已定義部分應用側操作的傳輸方式與資料結構。以下是已核對的外部 **Release 19** Stage 3 例子：

| 需求 | 操作與輸入 | 成功回覆 |
| --- | --- | --- |
| 向 ADAES 訂閱切片應用效能 | POST `{apiRoot}/ss-adae-sspa/<apiVersion>/slice-specific-application-performance`，使用 `SliceAppPerfSub` | `201 Created` 與 `Location`；後續通知使用 `SliceAppPerfNotif` |
| 向 AIMLE server 請求模型訓練 | POST `{apiRoot}/aimles-trn/v1/request-train`，使用 `TrainRequest` | `200 OK` 與 `MlModelTrainResp`；另有訓練通知與 OpenAPI 定義 |

這表示不同提供者有可共同遵循的操作契約。實際互通仍需共同支持相應版本、API 與授權條件；涉及模型、特徵或中間結果時，也需核對這些內容是否已有一致定義。上述 Release 19 例子不證明全部 Release 20 新程序已有同版本 Stage 3 覆蓋。

服務發現也有不同目標：CAPIF 支援 SEAL API 的發布與發現；AIMLE 的 server discovery 則從已知 AIMLE server URI 出發，尋找符合任務條件的另一個 server。後者仍有已知入口，不能用來回答所有服務如何從零互相發現。

### 6.3. NWDAF 參與應用 ML 的另一條線索

AIMLE 的 split operation pipeline discovery 提到，可用處理節點可以包含 VAL servers、NWDAFs，操作例子包括 inference。AIMLE client 取得 pipeline profile 後，可以把端點資訊交給 VAL client 使用。

因此，「AIMLE 與 NWDAF 只會交換既有分析」過於絕對。但這個發現也不能直接證明 NWDAF 可執行任意應用模型：目前讀到的節點登記程序描述 VAL server，尚未補齊 NWDAF 如何提供能力資訊、接受模型、對應 pipeline 端點及 Nnwdaf 操作。

後續可以沿這條具體線索查證互動條件。至於 AIMLE／ADAE 能否取代某項 NWDAF 能力，則需指定該能力逐項比較，不能在整體名稱上判斷包含關係。

**討論時間：37:55–42:27。**

**原討論摘要：** 老師提出核網 AI 與應用 AI 看起來分成兩個世界的觀察，並假設 AIMLE／ADAE 更有彈性，追問為何不直接用它們完成 NWDAF 的工作。接著詢問不同公司各自提供應用服務時，彼此如何互通。報告者表示尚未確認應用側規格的詳細能力與限制。老師也回到最初關切的非核網資料來源，以及應用如何使用網路能力。

## 7. 自訂 Analytics ID 之後，訓練任務如何真正執行

核心問題是：即使 AF 可以提出自訂 Analytics ID，NWDAF 收到後究竟用什麼資料、跑什麼模型、交換什麼資訊？

### 7.1. ID 識別任務，參與端仍須支持任務內容

**自訂 ID 是擴充入口，不會自動產生資料來源、模型或演算法。** 要讓任務執行，參與的 NWDAFs 必須真正支持該 ID 所代表的工作。

允許非標準 Analytics ID 的明確註解位於 untrusted AF 作為 VFL server 的程序。它要求這些 ID `need to be supported by NWDAFs acting as VFL clients`，operator 也負責確保 PLMN 內的非標準 ID 唯一。因此，這段不能擴張成任意 AF 發送未知 ID，NWDAF 就會自行建立新分析。

### 7.2. 從 ID 到可執行任務還需要什麼

對一個自訂任務，至少需要讓各端對以下內容有一致理解：

| 需要釐清的內容 | 缺少時會遇到的問題 |
| --- | --- |
| 預測目標及標籤由誰提供 | 不知道模型要學習什麼、如何計算訓練結果 |
| 各端持有哪些樣本與特徵 | 不知道哪些端能參與，也無法確定共同樣本 |
| 樣本識別、對齊方式與時間窗 | 各端的中間結果可能無法對應同一對象與時間 |
| 本地模型、計算與交換格式 | 收到中間資訊後不知道如何解析及更新模型 |
| 推論時需要哪些端與輸入 | 訓練完成仍可能無法產生目標分析結果 |

這是依 VFL 準備、訓練與推論程序歸納的對接需求，並非規格另定的一套完整自訂 ID schema。TS 23.288 §6.2H.3 明說部分中間內容 `The content is not standardized in this Release.`，feature ID 的值也未標準化。因此，選定 ID 後還需要建立共同的模型與資料契約。

### 7.3. 外部資料有入口，但要核對它送的是什麼

已有的 UE Application 資料收集程序允許 UE application 經 user plane 提供資料給 Data Collection AF，再由 AF 依 SLA、同意及所訂閱事件處理，直接或經 NEF 提供給 NWDAF，用於分析與模型訓練。

這可以作為外部資料入口的線索，但仍需確認所需特徵是否包含在該資料收集事件及格式中。原始應用資料、HFL 的模型參數、VFL 的中間結果，是不同的交換內容；不能因為都來自 UE／邊緣端，就假設可以走同一條資料收集程序。

目前尚未選定任務、dataset 與演算法，因此不能確認某個自訂 ID 已有可執行模型，或 NWDAF 已能取得全部特徵。下一步應接續第 4、5 題，逐項追蹤資料的產生者、傳遞介面、模型持有者及實際計算。

### 7.4. 原討論與規格依據

**討論時間：55:39–58:04。**

**原討論摘要：** 報告者提出 AF 使用非標準 Analytics ID 的規格註解，認為可能支持外部任務。老師回應，觸發訓練開始之後，真正執行時所使用的資料來源與模型內容仍是基本問題。接著詢問 NWDAF／MTLF 與邊緣設備是否有實際互動機會。報告者表示還不知道規格保留的彈性到哪裡，也未確認理想情境需要哪些規格外設計。
